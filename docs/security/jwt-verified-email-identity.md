# Verified email in gateway JWT identity lookup

Gateway JWT authentication accepts an email for account lookup, legacy email linking, new-user email storage or existing-user email backfill only when the authenticated claims contain the Boolean `email_verified: true` and the selected address exactly equals the canonical `email` claim. Missing, null, false, string and numeric verification values do not establish ownership. This also applies when email is explicitly configured as the user ID or is the fallback for a missing user ID, including issuer-specific normalized mappings. Nested identity paths ending in `email`, such as `user.email` and `metadata.user.email`, require the same check even without a separate email mapping

Configured stable user IDs continue to resolve their existing accounts without an email claim. Email-backed RBAC object IDs and virtual-key mappings enforce the same ownership check before selecting a cached account or key. Issuer normalization excludes unverified email identities, including their internal aliases. An unverified email cannot select another account, populate its cached identity or trigger the fuzzy lookup's SSO identity update

The email-verification predicate applies at the JWT boundary. The shared account lookup also rejects ambiguous email matches and refuses to replace an established subject binding for every caller, including non-JWT SSO. First-time linking conditionally writes an unbound row and rereads the committed identity before returning it. Existing subject matches and unambiguous email-only lookups remain supported; a failed link does not prove that the surrounding SSO flow will reject its separate registration path

Email-only gateway JWT deployments must supply the provider's verified canonical email assertion or configure and provision a stable subject identity. Custom email claim mappings must equal the verified canonical email; a verified address cannot authorize a different mapped address. An email-domain allowlist does not prove ownership. These changes do not modify an identity provider, application login configuration, existing user records or runtime settings

This corrects the JWT email account-selection paths described in [CVE-2026-93355's disclosure](https://www.ox.security/blog/litellm-an-ordinary-login-token-can-become-someone-elses-admin-account/). The verification/value binding follows [OpenID Connect's standard claims](https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims); [its identity guidance](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability) distinguishes stable issuer/subject identity from changeable email addresses. Synthetic signed-token and database/cache regressions demonstrate the source correction; they do not establish deployment or repair any previously altered account binding
