# Image evidence for the semantic-cache backport

LiteLLM remains version 1.100.0. CVE-2026-89032 is repaired by the reviewed semantic-cache scope lookup and authenticated metadata sanitization. The Image Scan workflow proves both installed modules match their literal reviewed SHA256 values before generating an OpenVEX `fixed` statement. It runs 36 tenant-scope cases, eight authenticated route/metadata-form cases, and the existing shared-key behavior with synthetic identities, no provider calls, and container networking disabled

The proof runs the image's installed Python distribution using isolated Python, a read-only root filesystem, and no source mounts. Both imported module locations must match the installed distribution. The job joins the checkout commit, committed proof scripts, Docker revision label, Docker config ID, registry manifest bytes, and immutable repository digest. Changes to either repaired module require a fresh source review and explicit hash update; a version label alone cannot satisfy this proof

The job uses a digest-pinned registry bound only to loopback to give the locally built image a real registry manifest digest. Nothing is published to an external registry. Grype 0.114.0 identifies VEX image products using repository digests; a Docker config ID or an OCI archive manifest alone is insufficient. The generated statement names the exact image digest and `pkg:pypi/litellm@1.100.0` subcomponent. Package-only, tag-only, other-image, or other-package assertions are not generated

The first Grype JSON report retains the existing `--only-fixed` disposition, including unfixed findings in `ignoredMatches`, before VEX is supplied. The second uses native Grype VEX with the unchanged `--only-fixed --fail-on high` policy. Validation requires the same database and image, preserves every original finding, and permits only this CVE and its exact alias on the proven installation to move into the VEX `fixed` disposition. Every other finding the existing policy blocks still blocks. Raw JSON, adjudicated JSON, OpenVEX, installed proof, and file hashes are retained as CI artifacts, including when a remaining vulnerability blocks release

OpenVEX author text is not a cryptographic signature. These are job-produced evidence artifacts whose custody comes from the exact reviewed workflow and normal CI artifact delivery. They do not authorize an arbitrary external VEX document or establish that another image is repaired. The behavioral regressions reject the original cache implementation and the repaired cache combined with the original identity sanitizer; metadata-container lookup alone is insufficient

GitHub proves its `docker/Dockerfile.non_root` build. The final image published by GitLab is a separate immutable artifact. Before deployment, rerun the installed proof and scan on that actual published image, preserving its original registry digest and Docker config ID and joining any loopback copy to that same original image. A successful GitHub fixture or build does not establish the installed-source closure of the final GitLab image

The existing GitLab container gate remains unchanged and rejects every High/Critical finding in its actual report. The retained successful analyzer 8.6.35/Trivy 0.72.0 report used the analyzer's normal OS-package scan and contained no Python/LiteLLM component. It is not evidence that Trivy measured or adjudicated this Python CVE. No GitLab exception or new language-scan policy is introduced
