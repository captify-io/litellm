# Image evidence for the semantic-cache backport

LiteLLM remains version 1.100.0. CVE-2026-89032 is repaired by the reviewed semantic-cache scope lookup and authenticated metadata sanitization, including removal of client-supplied cache-key overrides at the HTTP boundary. The active image proof is `scripts/semantic_cache_backport.py`, with reviewed source hashes in `security/backports/CVE-2026-89032.json`. It runs 36 tenant-scope cases and 12 proxy cases with synthetic identities, no provider calls, and container networking disabled

The active proof runs inside the image by immutable Docker config ID, as a non-root user with a read-only root filesystem and no source mounts. It binds the installed source hashes, checkout commit, Docker revision label and inspected image identity. Changes to either repaired module require source review and an explicit hash update

GitHub builds `docker/Dockerfile.non_root` with the exact source revision label and commit-specific local tag. After the offline migration and attestation rejection tests, `prepare` binds that tag to its Docker config ID and writes the installed proof and OpenVEX. Both Grype scans use `docker:<config ID>`. The first retains the raw findings, then `verify` repeats the image/source/behavior checks before the second scan uses the same database and the existing `--only-fixed --fail-on high` threshold. The VEX product names the verified local commit tag and `pkg:pypi/litellm@1.100.0` subcomponent. The tag is never accepted without the source, config-ID and behavior checks

GitLab qualifies its separately published image. `attest-image-backport` runs the installed proof on the exact registry digest emitted by `build-image`. The container analyzer fetches the same source and uses `scripts/verify_semantic_cache_backport.rb` to recompute the proof and VEX binding before both normal `gtcs scan` invocations. Language-package scanning is enabled. The first report is retained without VEX, the second uses the exact-image VEX and unchanged database, and the report comparison refuses any unrelated finding removal or change. The existing High/Critical release gate still evaluates the final report

OpenVEX author text is not a cryptographic signature. These are job-produced evidence artifacts whose custody comes from the exact reviewed workflow and normal CI artifact delivery. They do not authorize an arbitrary external VEX document or establish that another image is repaired. The behavioral regressions reject the original cache implementation and the repaired cache combined with the original identity sanitizer; metadata-container lookup alone is insufficient

Raw findings, adjudicated reports, OpenVEX and installed proof remain CI artifacts even when another vulnerability blocks release. A successful GitHub build does not establish the installed-source closure of the final GitLab image

The older standalone command `scripts/security/image_backport.py` remains available for a caller that supplies a job-local loopback registry digest, exact source revision and Grype binary. It verifies registry manifest bytes, the Docker config, installed distribution paths and the current literal source hashes. Its compatibility probe retains 36 tenant-scope cases, eight metadata-form route cases and one shared-key control. It does not replace the active probe's cache-key override cases. Its raw scan retains `--only-fixed`, and its adjudication checks permit only this CVE or its exact alias on the proven installation to enter the VEX `fixed` disposition. Its parser, identity and report-rejection tests continue running in the GitHub workflow
