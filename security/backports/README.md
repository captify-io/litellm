# Source-bound security backports

CVE-2026-89032 is fixed in this fork without changing the `litellm` package version or claiming the complete upstream 1.101 release. The code includes the metadata lookup correction from upstream commit `16db51e2cfc28e02bd460481e634a8403ea9265e`, plus HTTP-boundary closure of client-controlled bare `user_api_key`, root `cache_key`, and nested `litellm_params.preset_cache_key`. Trusted in-process SDK and server-generated keys retain their behavior.

The backport manifest pins the exact two reviewed source files. The guard requires a clean checkout at the pipeline commit, a rootless candidate with that revision label, the expected installed package version and exact installed file hashes. It runs 36 metadata/backend cases and 12 composed HTTP preprocessing/cache-handler cases inside the inspected immutable Docker configuration ID with networking disabled, a read-only filesystem, user 65534, dropped capabilities and no new privileges. No model request is made. Missing, changed or incomplete proof fails the job.

The generated OpenVEX statement says `fixed` for exactly this CVE and `pkg:pypi/litellm@1.100.0` in the verified artifact. It is not a general ignore, a `not_affected` claim, or a package version override. Source/manifest/guard drift requires a new reviewed proof; do not update hashes merely to make a scan pass.

GitHub scans the inspected immutable Docker ID. Its VEX product is the unique source-SHA tag retained in the image's actual RepoTags; the tag is never represented as a registry digest. The guard reruns immediately before the gated scan. Raw Grype JSON and gated JSON with suppressed matches, proof and VEX are retained. The incumbent `--only-fixed --fail-on high` policy is unchanged: unrelated fixable High/Critical findings block, and unknown/unfixed findings remain visible in the raw report.

GitLab's Docker-capable predecessor pulls the actual emitted registry digest and runs the installed-image probe. The normal analyzer consumes that immutable digest, not a tag. It fetches the same source and uses its existing Ruby/Git runtime to recompute the source, manifest, both guard hashes, proof and fixed VEX before each normal `gtcs scan`. The analyzer does not rerun the in-image probe or require Docker. Native Trivy VEX support filters the second scan using the same cached database. A report comparison preserves every suppressed row and refuses removal of any other CVE/package/version or changes to retained findings. The normal High/Critical release gate consumes the unmodified filtered scanner report. Python/language scanning is explicitly enabled.

The raw report, filtered report, proof, VEX and suppressed-finding summary must remain together. A `fixed` statement is generated only after behavior and installed-source proof; the scanner result alone is not evidence the code was repaired. CI must not publish/deploy if any proof or normal security gate fails.
